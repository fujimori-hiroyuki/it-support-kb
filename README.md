# it-support-kb

ITサポートの**ナレッジベース（事例集）原本**リポジトリ。

## 目的・方針

- 問い合わせ・トラブルは毎回違う「見え方（症状の言い回し）」で発生する。人間の全文検索では既存事例に該当すると気づきにくい。
- そこで、事例を **YAML で多面的に構造化**し（症状は複数の言い回しを配列で保持、原因・対象・局面を分離）、**AI(Kiro)が意味で関連事例を橋渡し**できる「AIが引く台帳」とする。
- **YAML が唯一の原本**。人間向けの手順書（やさしい言葉のステップ）は、この原本から生成する**副産物**。
- 現在は**一人運用の試行段階**。スキーマは固定せず、事例を貯めながら育てる。共同編集は形が固まってから。

## 構成

| パス | 役割 |
| --- | --- |
| `cases/*.yml` | 事例の構造化原本（1ファイル1事例、または関連事例をまとめる） |
| `README.md` | 本ファイル |

## 事例スキーマ（検証中・増減する）

フィールドは「索引（引くための鍵）」と「本文（引いた先の中身）」に分けて捉える。

### 索引（多面的な入口。同じトラブルの違う"見え方"を吸収する）
- `symptoms`: ユーザーから見えた現象（言い回しの揺れを配列で複数）
- `keywords`: 追加の検索語（製品名・エラー文言など）
- `category` / `targets`（関係する機器・ソフト）/ `context`（どんな局面で起きるか）

### 本文（索引で引いた先の、再利用可能な知識）
- `root_cause`: 技術的な真因（ここが同じ事例同士を `related` で繋ぐ）
- `resolution`: 対処の要点。詳細手順があれば `doc_ref`

### その他
- `id` / `title` / `related`（関連事例id。半自動: Kiroが提案→人が承認）/ `severity` / `status`

> 検討中(次の事例で試す): 本文が薄いので「診断」層を足すか。同じ症状でも真因が複数ありうる
> （例「メールが見られない」= pst未移行 / プロファイル破損 / アーカイブ退避）。その切り分けを
> 本文に持たせる案 → `diagnosis`(切り分け) / `cause`(なぜ起きるか) / `resolution` /
> `verification`(直った確認) / `caveats`(注意・落とし穴)。1件では要否不明なので固定しない。

## 別PCでの継続

1. `git clone <このリポジトリURL>`
2. Kiro で開いて作業。事例追加は「この問い合わせを登録して」と依頼すれば、散文からKiroが構造化YAMLに落とす。
3. 前提: git（と、集計等を足す場合は Python3）。

## 保守フロー（日々の運用ルール）

日々の障害対応スピードの中で、リポジトリを保守しつつノウハウを蓄積するための運用。
**台帳（毎日・軽い）とKB（週一・数件）を分離し、構造化はAI(Kiro)に寄せる**のが原則。

### 1. 台帳とKBを分ける

- **台帳（記録）**: 障害が起きたら1行追加するだけ。スピード優先。CSV/スプレッドシート（例: `ディフィカルティ一覧.csv`）で管理。台帳そのものは原本にしない（`_work` 等に置く）。
- **KB（再利用ナレッジ）**: `cases/*.yml`。時間をかけて構造化する。**毎回はやらない。効くものだけ。**

この2つを同じ速度で回そうとしない。台帳は毎日、KBは週一でよい。

### 2. 週次リズム（報告作成に相乗りさせる）

週一報告のために台帳はどのみち見返す。その瞬間をKB化のトリガーにする。

1. **日々**: 障害発生 → 台帳に1行（No/日/拠点/症状/解決状況/工数）。KBのことは考えない。
2. **週一（報告時）**: 今週の行をレビューし、KB化する数件だけを指さす。
3. **KB化はKiroに投げる**: 「この台帳の行を事例にして」と依頼 → 脱機微化・構造化・related付けまでKiroが実施。人間は判断だけ。

### 3. KB化の判断基準（全部はやらない）

次のいずれかに当てはまるものだけ `cases/` に起こす。それ以外は台帳止まりでよい。

- **2回目に遭遇した**（1回目は台帳のみ）
- **複数拠点/複数回で発生**（横展開の価値がある）
- **切り分けに30分以上悩んだ**（次に同じ時間を溶かさないため）
- **他事例と根が繋がる**（related で橋渡しできる）

逆に「一度きり・その場対応で完了・再利用しない」ものは、解決済みでもKB化不要。

### 4. 未解決/仮説でも登録する（解決を待たない）

- 解決してからKB化しようとすると、忙しさで永遠に書かれない。**切り分けた時点の `status: draft` が最も価値がある。**
- 真因が確定していなければ仮説として書き、`caveats` に留保を明記する（例: iphone-xr-call-mic, network-slow-getsumoku）。
- 解決・真因確定したら `draft` → `confirmed` に上げる。

### 5. 報告書は原本から生成する（一石二鳥）

- 週次報告のサマリ（対応件数/工数/未解決リスト）や、現場要求リストは、台帳/KBから**生成物として出す**。手で書き直さない。
- これによりKB保守が「報告の副産物」になり、追加コストがほぼゼロになる。

### 6. 完璧を目指さない（破綻回避）

- related の全網羅、全件 `confirmed` 化などを追い求めない。「AIが意味で引けるようになれば十分」で妥協する。
- 台帳の記入だけは最低限守る（「何が・どこで・どうなった」の一言）。症状が空の行はKB化できない。

> この運用は「保守はAI(Kiro)が前提」という本リポジトリの方針を実務速度で成立させるためのもの。
> 人間が手でYAMLを書く運用だと日々の障害対応速度には追いつかない。構造化はKiroに寄せること。
